# Архитектура Turnirium

## Цель структуры

Turnirium остаётся локальным монолитным приложением: один процесс FastAPI владеет SQLite-БД и обслуживает браузерные рабочие места по HTTP/WebSocket. Внутри процесса код разделён на слои, чтобы изменение турнирной логики не требовало одновременно править HTTP, UI и Windows-оболочку.

## Слои

### `app/routes/` — HTTP API

Маршруты сгруппированы по предметным областям:

- `tournaments.py` — турниры и площадки;
- `participants.py` — участники, импорт и экспорт списка;
- `categories.py` — CRUD категории, правила, состав и посев;
- `category_stages.py` — генерация и перестройка групп, Swiss, олимпийки/плей-офф и выдача таблиц;
- `matches.py` — счёт, предупреждения, результат и таймер;
- `schedule.py` — очереди и текущий бой площадки;
- `templates.py` — шаблоны правил;
- `exports.py` — выгрузка результатов и компактный публичный статус;
- `system.py` — системная информация, брендинг и выбор БД;
- `maintenance.py` — резервные копии, аудит и очистка;
- `public.py` — агрегированные данные публичного экрана;
- `schemas.py` — входные модели и централизованная валидация API.

Маршрут должен проверить входные данные и допустимость состояния, вызвать предметный сервис, зафиксировать/получить результат и отправить WebSocket-событие. Алгоритмы жеребьёвки, продвижения по сетке и расчёта мест в маршрутах размещать не следует.

### `app/services/` — предметная логика

- `brackets.py` — олимпийская сетка, BYE и бронзовый бой;
- `groups.py` — группы и «все со всеми»;
- `swiss.py` — швейцарская система;
- `playoffs.py` — плей-офф после групп;
- `standings.py` — таблицы и итоговые места;
- `scheduling.py` — назначение и оптимизация очередей;
- `matches.py` — жизненный цикл боя, предупреждения, корректировки и статус участника;
- `maintenance.py` — резервное копирование и очистка;
- `common.py` — небольшие общие предметные функции.

`app/engine.py` сохранён только как совместимый фасад старых импортов. Новую предметную логику следует добавлять в соответствующий модуль `services`, а не расширять фасад реализацией.

### `app/models.py`, `app/db.py` — хранение данных

`models.py` содержит SQLAlchemy-модели. `db.py` отвечает за создание движка, локальные лёгкие миграции, выбор SQLite-файла и жизненный цикл сессий. Только серверный процесс открывает БД; браузеры никогда не работают с SQLite напрямую.

Изменения, затрагивающие несколько связанных сущностей, должны выполняться одной транзакцией. Внутренние сервисы могут принимать `commit=False`, если ими управляет более крупная атомарная операция.

### `app/static/` — браузерный интерфейс

Клиентский код разделён по экрану и ответственности:

- `common.js` — HTTP, WebSocket, общие форматтеры и диалоги;
- `admin.js` — каркас организатора, участники, расписание, сеть и сервис;
- `categories.js` — категории, правила, группы, Swiss и сетки;
- `secretary.js` — рабочее место секретаря;
- `board.js` — табло площадки;
- `public.js` — общий экран;
- `bootstrap.js` — выбор нужного экрана по URL.

Стили разделены на базовые, соревновательные, экранные, сетевые, категорийные и сервисные CSS-модули. Порядок их подключения в `index.html` сохраняет каскад.

Функции конкретного экрана не следует переносить в `common.js`, если ими не пользуются минимум два экрана.

### Windows-оболочка

`desktop.py` запускает сервер, показывает адреса и управляет системным треем. Она не содержит турнирной логики и обращается к приложению через HTTP/API либо общие инфраструктурные функции.

## Направление зависимостей

Предпочтительное направление:

`routes -> services -> models/db`

`static -> HTTP/WebSocket API`

`desktop -> main/system API`

Сервисный слой не должен импортировать HTTP-типы FastAPI. Модели не должны импортировать сервисы или маршруты.

## Ошибки и транзакции

Ожидаемые нарушения предметных правил сервисы сообщают через `ValueError`; HTTP-слой преобразует их в `409 Conflict`. Ошибки валидации входного запроса возвращаются Pydantic как `422`. Ошибки чтения пользовательского файла могут возвращать `400`.

Неожиданные исключения не следует подавлять без причины. Если широкое исключение намеренно перехватывается на инфраструктурной границе — экспорт, резервное копирование, работа с ОС, сеть — причина должна быть локальной и понятной, а исходное исключение должно сохраняться через `raise ... from exc`, где это уместно.

## Ограничения размера кода

Автотесты архитектуры применяют верхние границы:

- Python/JavaScript/CSS-модуль — не более **600 строк**;
- Python-функция — не более **150 строк**;
- Python-класс — не более **500 строк**.

Это страховка от повторного появления монолитов, а не цель сама по себе. Если модуль начинает объединять несколько разных ответственностей, его следует разделять раньше достижения лимита.
